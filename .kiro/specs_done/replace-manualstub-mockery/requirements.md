# Requirements Document

## Project Description (Input)

Looking at the current Go test code, it contains manually created stubs and mocks, rather than code automatically generated by mockery (<https://github.com/vektra/mockery>).

What I want to do:

- Replace the existing manually created stubs and mocks with code generated by mockery.
- Place the generated mock implementation files in the corresponding package. For packages in /pkg, create a mock directory in the same package and store them there. For packages under internal, create a mock directory in the corresponding package on the infrastructure side and store them there.
- Create Claude's skills to use mockery whenever mocks are needed.

## Introduction

This spec covers the replacement of all manually written test stubs and mocks in the go-crypto-wallet project with auto-generated mocks using the `mockery` v3 tool. The project already uses mockery for some interfaces (repository and file storage layers), but several interfaces remain without generated mocks, leading to manually written testify/mock wrappers and simple struct stubs in test files. The goal is a unified, consistent mock generation strategy across the entire codebase, accompanied by a Claude skill that encodes the workflow.

### Current State

- **Manual stubs** (simple structs): BTC keygen test files (`generate_descriptor_test.go`, `export_descriptor_test.go`) contain `stubAccountRepo`, `stubAuthRepo`, `stubSeedRepo`, `stubDescriptorGenerator`, `stubDescriptorFileWriter`, `stubAccountKeyRepo`.
- **Manual testify mocks**: XRP watch test files (`send_transaction_test.go`, `create_transaction_test.go`) contain `MockTransactionSubmitter`, `MockAccountInfoProvider`, `MockTransactionPreparer`.
- **Mockery-generated** (17 files, already correct): Repository mocks, file storage mocks, BTC API mock.
- **Gaps in `.mockery.yaml`**: ETH segregated interfaces, XRP use-case sub-interfaces, BTC keygen domain-specific interfaces (descriptor generator, file writer) are not configured.

## Requirements

### Requirement 1: Replace BTC Keygen Manual Stubs with Mockery-Generated Mocks

**Objective:** As a developer, I want BTC keygen test stubs replaced with mockery-generated mocks, so that stub maintenance is eliminated and mock behavior is consistent with the interface contract.

#### Scope

Affects:
- `internal/application/usecase/keygen/btc/generate_descriptor_test.go` (stubs: `stubAccountRepo`, `stubAuthRepo`, `stubSeedRepo`)
- `internal/application/usecase/keygen/btc/export_descriptor_test.go` (stubs: `stubDescriptorGenerator`, `stubDescriptorFileWriter`, `stubAccountKeyRepo`)

#### Acceptance Criteria

1. When `make mockery` is run, the Mockery Tool shall generate mocks for `BTCAccountKeyRepositorier`, `AuthFullPubkeyRepositorier`, and `SeedRepositorier` interfaces (already configured in `.mockery.yaml`) in their respective `mocks/` directories under the infrastructure layer.
2. When `make mockery` is run, the Mockery Tool shall generate mocks for any descriptor-generator or file-writer interfaces used in BTC keygen tests that are not yet listed in `.mockery.yaml`, placing them in the appropriate infrastructure `mocks/` directory.
3. When test stubs are replaced, the BTC keygen tests shall use `NewMock<InterfaceName>(t)` constructors and the `.EXPECT()` builder pattern from the mockery-generated mocks.
4. The Mockery Tool shall not generate mocks for simple value-object helpers that are not Go interfaces.
5. After replacement, the manually written stub structs (`stubAccountRepo`, `stubAuthRepo`, `stubSeedRepo`, `stubDescriptorGenerator`, `stubDescriptorFileWriter`, `stubAccountKeyRepo`) shall no longer exist in BTC keygen test files.
6. When `make go-lint` and `make check-build` are run after replacement, the build shall succeed with no lint errors.

### Requirement 2: Replace XRP Watch Manual Mocks with Mockery-Generated Mocks

**Objective:** As a developer, I want XRP watch-layer test mocks replaced with mockery-generated mocks, so that mock generation is automated and consistent with the rest of the project.

#### Scope

Affects:
- `internal/application/usecase/watch/xrp/send_transaction_test.go` (mock: `MockTransactionSubmitter`)
- `internal/application/usecase/watch/xrp/create_transaction_test.go` (mocks: `MockAccountInfoProvider`, `MockTransactionPreparer`)

#### Acceptance Criteria

1. When the interfaces `TransactionSubmitter`, `AccountInfoProvider`, and `TransactionPreparer` (or their equivalents in the XRP ports layer) are identified, the `.mockery.yaml` shall be updated to include them with `dir` pointing to `internal/infrastructure/api/xrp/mocks/`.
2. When `make mockery` is run, the Mockery Tool shall generate `mock_transaction_submitter.go`, `mock_account_info_provider.go`, and `mock_transaction_preparer.go` (or equivalent snake_case filenames) in the designated directory.
3. When test mocks are replaced, the XRP watch tests shall use `NewMock<InterfaceName>(t)` constructors and the `.EXPECT()` builder pattern.
4. After replacement, the manually written mock structs (`MockTransactionSubmitter`, `MockAccountInfoProvider`, `MockTransactionPreparer`) shall no longer exist in XRP watch test files.
5. When `make go-lint` and `make check-build` are run after replacement, the build shall succeed with no lint errors.

### Requirement 3: Add Mockery Configuration for ETH API Interfaces

**Objective:** As a developer, I want mockery-generated mocks for ETH segregated interfaces, so that ETH use case and integration tests can use consistent auto-generated mocks.

#### Scope

Affects:
- `internal/application/ports/api/eth/interface.go` (interfaces: `ETHLifecycle`, `ETHKeyAccessor`, `ETHTransactionSigner`, `TxCreator`, `GasEstimator`, `TxSigner`, `TxSender`, `TxMonitor`, and others as applicable)
- `.mockery.yaml` — add the `internal/application/ports/api/eth` package entry
- Generated output: `internal/infrastructure/api/eth/mocks/`

#### Acceptance Criteria

1. The `.mockery.yaml` shall include an entry for `github.com/hiromaily/go-crypto-wallet/internal/application/ports/api/eth` with `dir: "internal/infrastructure/api/eth/mocks"` and listing all segregated ETH interfaces.
2. When `make mockery` is run, the Mockery Tool shall generate one mock file per listed ETH interface in `internal/infrastructure/api/eth/mocks/`.
3. The generated mock file naming shall follow the existing convention: `mock_<interface_name_snakecase>.go`.
4. The Mockery Tool shall not generate a mock for the monolithic `Ethereumer` interface (used only in DI layer); only segregated interfaces shall be listed.
5. When `make go-lint` and `make check-build` are run after generation, the build shall succeed with no lint errors.

### Requirement 4: Generate Missing XRP API Mocks

**Objective:** As a developer, I want all XRP API interfaces configured in `.mockery.yaml` to have generated mocks on disk, so that XRP tests do not fall back to manual mocks.

#### Scope

Affects:
- `.mockery.yaml` (already configured: `Rippler`, `RippleAPIer`, `RipplePublicer`, `RippleAdminer`)
- Generated output: `internal/infrastructure/api/xrp/mocks/`

#### Acceptance Criteria

1. When `make mockery` is run, the Mockery Tool shall generate mock files for `Rippler`, `RippleAPIer`, `RipplePublicer`, and `RippleAdminer` in `internal/infrastructure/api/xrp/mocks/`.
2. The generated files shall contain the `// Code generated by mockery; DO NOT EDIT.` header.
3. When `make go-lint` and `make check-build` are run, the build shall succeed with no lint errors.

---

### Requirement 5: Enforce Mock Placement Convention in `.mockery.yaml`

**Objective:** As a developer, I want a documented and enforced convention for where mock files are placed, so that new interfaces always get mocks in the correct directory without manual decisions.

#### Acceptance Criteria

1. The `.mockery.yaml` shall follow the rule: for interfaces defined under `internal/application/ports/<layer>/<package>`, the `dir` shall point to `internal/infrastructure/<layer>/<package>/mocks`.
2. The `.mockery.yaml` shall follow the rule: for interfaces defined under `pkg/<package>`, the `dir` shall point to `pkg/<package>/mocks`.
3. When a new interface is added to `internal/application/ports/`, the corresponding mockery configuration entry shall be added to `.mockery.yaml` in the same commit or PR.
4. The Mockery Tool shall use `filename: "mock_{{.InterfaceName | snakecase}}.go"` and `structname: "Mock{{.InterfaceName}}"` patterns consistently across all configured packages.

---

### Requirement 6: Create a Claude Skill for Mockery Usage

**Objective:** As a developer using Claude Code, I want a skill that guides mock generation with mockery, so that I never need to manually write mocks when an interface changes or a new interface is introduced.

#### Acceptance Criteria

1. The Mockery Tool skill shall be stored at `.claude/skills/mockery/SKILL.md` (or the project's established skill path).
2. When a developer asks Claude to generate a mock for an interface, the Mockery skill shall instruct Claude to: (a) locate the interface definition, (b) determine the correct `dir` value using the placement convention from Requirement 5, (c) add the interface to `.mockery.yaml` if missing, (d) run `make mockery`, and (e) verify with `make go-lint` and `make check-build`.
3. The Mockery skill shall include the current `.mockery.yaml` placement convention, the `make mockery` command, and examples of before/after test code (manual stub → generated mock).
4. The Mockery skill shall document that mock files must never be manually edited (they are regenerated by `make mockery`).
5. The Mockery skill shall specify that tests shall use the `NewMock<InterfaceName>(t)` constructor and `.EXPECT()` pattern from testify/mock.
6. When the skill is invoked, Claude shall not create a new mock file manually but shall always use `make mockery` to regenerate all configured mocks.
